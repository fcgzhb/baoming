# Feature Specification: 旅游游学项目报名小程序平台

**Feature Branch**: `001-tour-signup-platform`
**Created**: 2026-07-13
**Status**: Draft
**Input**: User description: "我想开发一个微信小程序，核心功能是能够实现展示后台发布的旅游游学项目信息，然后用户能够在小程序内查看并报名。小程序端支持授权登录和微信支付订单。后台能够添加维护信息，查看用户信息和报名订单信息等基本功能。要求数据库使用myql即可"

## 概述

一个由两部分组成的微信小程序报名平台：

1. **小程序端（用户端）**：浏览游学项目、微信授权登录、填写报名信息、微信支付、查看我的订单。
2. **后台管理端（管理员）**：游学项目的发布与维护、用户信息查看、报名订单管理与在线退款。

数据存储使用 MySQL（用户明确要求）。

## Clarifications

### Session 2026-07-13

- Q: 敏感个人信息（证件号/手机号）如何保护与合规？ → A: v1 采用明文存储 + 单独授权同意记录，不做字段级加密（用户接受已知 PIPL 合规风险，加密存储列入后续迭代）。
- Q: 名额并发控制策略？ → A: 提交订单时校验剩余名额（满则禁止下单）+ 支付成功时原子扣减名额；待支付订单不锁定名额，并发支付中后到者支付失败并原路退款。
- Q: 报名/支付成功后如何通知用户？ → A: v1 不接入微信订阅消息推送，仅通过支付成功页与「我的订单」订单状态告知用户（维持原假设）。
- Q: 退款金额与名额/状态的关系？ → A: v1 仅支持全额退款（退款即全额 + 释放名额）；部分退款列入后续版本。
- Q: 同一参团人能否对同一项目重复报名？ → A: 不允许；同一项目下同一证件号同时仅能存在一条有效（待支付/已报名）订单，重复提交时拒绝并提示。
- Q: 报名表单字段固定还是按项目可配置？ → A: v1 采用固定字段集（姓名/证件/电话/与报名人关系/紧急联系人/就读学校·年级/备注）；按项目自定义字段（动态表单）列入后续迭代。
- Q: 后台是否需要数据导出？ → A: v1 不做导出，仅后台页面查看；订单/用户导出列入后续迭代。
- 用户指定（非提问）：后端使用 Node.js 开发；小程序端、后台管理端与后端代码置于**同一仓库目录**（monorepo 单仓库）。具体 Node 框架、monorepo 工具与后台前端技术留待 /speckit.plan 选型。

## Actors（参与者）

- **报名用户（End User）**：通过微信小程序浏览项目、报名、支付的用户；可为本人或他人报名（如家长替孩子）。
- **管理员（Admin）**：通过后台维护项目、查看用户、处理订单与退款。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 浏览并报名游学项目 (Priority: P1)

作为潜在学员/家长，我希望能在小程序里看到后台发布的游学项目列表与详情，以便了解项目并完成报名。

**Why this priority**：这是产品的核心价值闭环——没有「浏览→报名」，其他功能都失去意义，是 MVP 的最小可交付切片。

**Independent Test**：后台发布一个游学项目后，用户在小程序首页能看到该项目卡片，进入详情页能查看完整介绍/行程/价格/名额并能发起报名。仅此一条即可对外演示核心价值。

**Acceptance Scenarios**：
1. **Given** 后台已发布一个状态为「上架/报名中」的项目，**When** 用户打开小程序首页，**Then** 列表中看到该项目卡片（封面、标题、价格、报名状态）。
2. **Given** 用户在列表页，**When** 点击某项目卡片，**Then** 进入详情页，展示图文介绍、行程安排、出发/返回日期、价格、剩余名额、报名截止时间。
3. **Given** 项目详情页，**When** 名额已满或报名已截止，**Then** 报名按钮置灰并提示「名额已满/报名已截止」，无法继续报名。
4. **Given** 项目详情页且名额充足，**When** 用户点击「立即报名」，**Then** 进入报名信息填写页。

---

### User Story 2 - 微信授权登录 (Priority: P1)

作为用户，我希望通过微信一键授权登录，以便无需注册账号即可使用报名功能。

**Why this priority**：报名与支付都依赖已登录身份，P1；与 US1 同为 MVP 基石。

**Independent Test**：首次进入小程序触发登录、授权后系统能识别用户身份（微信 openid），并以该身份完成后续报名下单。

**Acceptance Scenarios**：
1. **Given** 用户未登录，**When** 触发需要登录的操作（如点击报名），**Then** 弹出微信授权登录。
2. **Given** 用户同意授权，**When** 系统获取微信登录凭证，**Then** 后端校验并建立用户会话，返回登录态；小程序后续请求携带该登录态。
3. **Given** 用户已登录且需要联系方式，**When** 引导授权手机号（微信手机号快速验证），**Then** 保存到用户资料。
4. **Given** 用户再次进入小程序，**When** 登录态仍在有效期内，**Then** 自动保持登录，无需重复授权。

---

### User Story 3 - 填写报名信息并微信支付 (Priority: P1)

作为报名用户，我希望填写参团人信息后用微信支付完成付款，以便锁定名额。

**Why this priority**：商业闭环的收银环节，直接产生订单与收入，P1。与 US1/US2 共同构成完整 MVP。

**Independent Test**：登录后对某项目填写一名参团人信息，调起微信支付，支付成功后能在「我的订单」看到一条「已确认/已报名」订单。

**Acceptance Scenarios**：
1. **Given** 用户在报名页，**When** 填写参团人信息（姓名、证件类型与号码、联系电话等），参团人可与登录用户不同（家长替孩子报名），**Then** 校验必填项与格式后允许提交。
2. **Given** 报名信息已提交且名额充足，**When** 用户确认订单并点击支付，**Then** 调起微信支付，金额为下单时锁定的项目价格。
3. **Given** 用户完成微信支付，**When** 收到微信支付成功回调，**Then** 后端校验回调签名与金额，将订单置为「已确认/已报名」并占用名额。
4. **Given** 支付被取消或失败，**When** 用户返回，**Then** 订单保留为「待支付」，可重新支付或关闭。
5. **Given** 并发抢最后名额，**When** 多人同时下单，**Then** 成功支付人数不超过项目总名额（不超卖）。

---

### User Story 4 - 查看我的订单 (Priority: P2)

作为用户，我希望在小程序里查看我的所有报名订单及状态，以便跟踪报名结果。

**Why this priority**：提升自助体验，非 MVP 闭环必需，P2。

**Independent Test**：用户完成至少一笔订单后，在「我的订单」看到该订单（项目名、金额、状态）并可按状态筛选。

**Acceptance Scenarios**：
1. **Given** 用户已登录且有历史订单，**When** 进入「我的订单」，**Then** 看到按时间倒序的订单列表（项目、金额、状态：待支付/已报名/已退款/已取消）。
2. **Given** 订单列表，**When** 点击某订单，**Then** 查看详情（参团人信息、支付时间、订单号）。
3. **Given** 一笔「待支付」订单，**When** 用户继续支付则重新调起支付；若取消则订单转「已取消」并释放名额。

---

### User Story 5 - 后台发布与维护游学项目 (Priority: P1)

作为管理员，我希望在后台创建、编辑、上下架游学项目，以便向小程序用户展示可报名的项目。

**Why this priority**：没有后台内容就没有前端可展示的内容，供给侧基础，P1。

**Independent Test**：管理员新建并上架一个项目后，小程序首页立即可见（对应 US1）。

**Acceptance Scenarios**：
1. **Given** 管理员已登录后台，**When** 新建项目并填写标题、封面图、图文介绍、行程安排、出发/返回日期、价格、总名额、报名截止时间，**Then** 保存为草稿或直接上架。
2. **Given** 已存在项目，**When** 管理员编辑并保存，**Then** 小程序端展示最新内容。
3. **Given** 已上架项目，**When** 管理员下架，**Then** 小程序列表不再展示（已产生订单不受影响）。
4. **Given** 某项目，**When** 报名人数达到总名额，**Then** 后台与小程序均显示「名额已满」。

---

### User Story 6 - 后台查看用户与订单、处理退款 (Priority: P1/P2)

作为管理员，我希望查看用户信息与订单明细，并能为需退款的订单发起在线退款，以便完成运营与售后。

**Why this priority**：订单查看与名额管理是运营必需（P1）；在线退款是售后闭环（P2）。

**Independent Test**：后台订单列表能筛选出某项目的全部订单；对其中一笔发起退款，成功后订单转「已退款」且名额释放。

**Acceptance Scenarios**：
1. **Given** 管理员进入订单管理，**When** 按项目/状态/手机号/姓名/订单号筛选，**Then** 看到匹配订单与汇总。
2. **Given** 订单列表，**When** 点击某订单，**Then** 查看订单与参团人详情。
3. **Given** 一笔「已报名/已支付」订单，**When** 管理员发起退款（全额或部分），**Then** 调用微信支付退款接口原路退回；退款成功回调后订单置「已退款」并释放名额。
4. **Given** 管理员进入用户管理，**When** 查看用户列表，**Then** 看到用户基本信息（昵称、头像、手机号、注册时间）及订单数。
5. **Given** 退款请求，**When** 微信退款异步回调到达，**Then** 系统校验并更新退款状态，保证与实际资金一致。

---

### Edge Cases（边界与异常）

- **支付掉单**：用户已付款但未返回小程序或回调延迟 → 需通过对账/查询补单，避免「付了钱但订单仍待支付」。
- **重复支付**：同一订单被重复发起 → 仅允许一笔有效支付，其余拒绝或自动跳转。
- **重复报名**：同一项目下同一证件号再次提交 → 拒绝并提示「该参团人已报名」（见 FR-015）。
- **名额并发竞争**：多人同时对最后名额发起支付 → 仅首个支付成功扣减名额，其余原路退款，保证不超卖（见 FR-010）。
- **退款失败/处理中**：微信退款返回失败或处理中 → 订单状态准确反映，允许管理员重试。
- **项目下架后有未完成订单**：已存在的「已报名」订单保留可查，不影响退款。
- **授权被拒**：用户拒绝授权登录/手机号 → 给出清晰提示与重试入口，不阻塞浏览。
- **订单取消后名额释放**：待支付订单超时或主动取消后，名额及时回补。
- **下单期间改价**：若管理员在用户下单期间调整价格 → 以用户下单时锁定的价格为准。
- **未成年人/证件**：参团人信息支持多种证件类型（身份证/护照/户口本等）。

## Requirements *(mandatory)*

### Functional Requirements

**用户端（小程序）**

- **FR-001**：系统 MUST 支持微信小程序授权登录（基于微信登录态/openid 识别用户），并在登录态有效期内保持登录。
- **FR-002**：系统 MUST 获取并保存用户授权的微信资料（昵称、头像）及手机号（用于联系）。
- **FR-003**：系统 MUST 在小程序首页展示后台已上架的游学项目列表（封面、标题、价格、报名状态）。
- **FR-004**：系统 MUST 提供项目详情页，展示图文介绍、行程安排、出发/返回日期、价格、剩余名额、报名截止时间。
- **FR-005**：系统 MUST 在名额已满或报名已截止时禁止报名并给出明确提示。
- **FR-006**：系统 MUST 支持填写参团人固定字段集：姓名、证件类型、证件号、联系电话、与报名人关系、紧急联系人（姓名+电话）、就读学校/年级、备注；参团人可与登录用户不同（为他人报名）。按项目自定义字段列入后续迭代。
- **FR-007**：系统 MUST 对参团人信息进行必填与格式校验（如证件号格式）。
- **FR-008**：系统 MUST 接入微信支付，允许对报名订单发起支付，金额为下单时锁定的项目价格。
- **FR-009**：系统 MUST 在收到微信支付成功回调后校验签名与金额，确认后将订单置为「已确认/已报名」并占用名额。
- **FR-010**：系统 MUST 防止名额超卖——提交订单时校验剩余名额（满则禁止下单），支付成功时以原子方式扣减名额；并发支付中后到者支付失败并原路退款，保证最终「已报名」人数不超过总名额。
- **FR-011**：系统 MUST 提供「我的订单」功能，支持按状态（待支付/已报名/已退款/已取消）查看列表与详情。
- **FR-012**：系统 MUST 支持对待支付订单继续支付或取消（取消后释放名额）。
- **FR-013**：系统 MUST 处理支付掉单（支付成功但回调缺失时能补单对账）。
- **FR-014**：系统 MUST 在采集参团人证件号、手机号等敏感个人信息前，获取用户单独授权同意，并记录同意时间与隐私协议版本。
- **FR-015**：系统 MUST 保证同一项目下同一参团人证件号同时仅能存在一条有效（待支付或已报名）订单；重复报名时拒绝并提示「该参团人已报名」。

**后台管理端**

- **FR-101**：系统 MUST 提供管理员登录（账号密码）。
- **FR-102**：系统 MUST 支持游学项目的创建、编辑、上架/下架、删除（软删除），含标题、封面、图文介绍、行程、日期、价格、总名额、报名截止时间。
- **FR-103**：系统 MUST 支持按项目/状态/手机号/姓名/订单号筛选与查看报名订单列表及详情。
- **FR-104**：系统 MUST 支持查看用户列表（昵称、头像、手机号、注册时间、订单数）与用户详情。
- **FR-105**：系统 MUST 支持管理员对「已支付/已报名」订单发起全额在线退款，调用微信支付退款接口原路退回（部分退款列入后续版本）。
- **FR-106**：系统 MUST 根据微信退款异步回调更新订单退款状态，并保证状态与实际资金一致。
- **FR-107**：退款成功后系统 MUST 将订单置为「已退款」并释放对应名额。
- **FR-108**：系统 MUST 记录订单状态变更与退款操作的关键日志（操作人、时间、金额）以便追溯。

### Key Entities（核心数据实体）

- **游学项目 (Project/Tour)**：标题、封面图、图文介绍、行程安排、出发/返回日期、价格、总名额、已报名人数、报名截止时间、上架状态。→ 拥有多条报名订单。
- **用户 (User)**：微信 openid、unionid（如有）、昵称、头像、手机号、注册时间。→ 拥有多条订单。
- **参团人 (Participant)**：姓名、证件类型、证件号、联系电话、与报名人关系、紧急联系人（姓名+电话）、就读学校/年级、备注等固定字段（v1 证件号与手机号明文存储，不做字段级加密；自定义字段后续迭代）。隶属某条订单（单人）。
- **授权同意记录 (Consent Record)**：所属用户、同意类型（如敏感信息采集）、隐私协议版本、同意时间。用于满足合规留痕。
- **报名订单 (Order)**：订单号、所属项目、报名用户、参团人信息、下单时锁定价格、订单状态（待支付/已报名/已退款/已取消）、支付时间、微信支付交易号、退款金额与状态（v1 仅全额退款）、创建/更新时间。→ 关联一个参团人，占用一个名额；同一项目下同一证件号唯一（不可重复报名，见 FR-015）。
- **管理员 (Admin)**：账号、密码（加密）、角色/权限（单角色 v1）。
- **操作日志 (Audit Log)**：操作类型、操作人、目标对象、金额、时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：用户从打开小程序到完成一笔报名支付的完整路径，可在 3 分钟内完成（授权→浏览→报名→支付）。
- **SC-002**：常规网络下小程序首页项目列表在 1 秒内加载并可见。
- **SC-003**：并发报名场景下，任意项目最终「已报名」人数绝不超出总名额（超卖率 0）。
- **SC-004**：至少 95% 的支付成功订单，其「已确认」状态在微信支付回调到达后 10 秒内更新可见；掉单情况可通过对账在合理时间内补正。
- **SC-005**：管理员发起的在线退款，订单状态与实际退款资金保持一致（差异率 0）。
- **SC-006**：管理员创建/上架新项目后，小程序端在合理刷新内即可见。
- **SC-007**：90% 的目标用户（家长/学员）能在无指导下独立完成一次报名。

## Assumptions（假设）

- 平台已具备微信小程序开发资质（AppID、AppSecret）与微信支付商户资质（商户号、API 密钥/证书），且已开通「小程序支付」。
- 游学项目由运营方人工录入维护，暂不支持第三方系统对接导入。
- 参团人为单人/订单（用户已确认）；一单多人为后续版本，v1 不纳入。
- 报名表单为固定字段集（v1，用户已确认）；按项目自定义字段（动态表单）为后续版本。
- v1 后台不支持数据导出（订单/用户），仅页面查看（用户确认）；导出功能列入后续迭代。
- 报名确认 = 微信支付成功即确认，无需后台审核（用户已确认）。
- 退款走后台在线退款，调用微信支付退款接口原路退回；v1 仅支持全额退款（用户确认），部分退款列入后续版本。
- 数据库使用 MySQL（用户明确要求），字符集按中文场景默认 utf8mb4。
- 技术栈与工程结构（用户明确要求）：后端使用 **Node.js**；小程序前端、后台管理前端与后端代码放在**同一仓库目录**（monorepo 单仓库）。Node 框架、monorepo 工具与后台前端技术栈留待 `/speckit.plan` 选型。
- v1 对参团人证件号、手机号采用明文存储（不做字段级加密），仅记录用户单独授权同意；已知存在 PIPL 合规风险，字段级加密与留存/脱敏策略列入后续迭代。
- v1 管理后台为单一管理员角色；细粒度权限/多角色为后续迭代。
- v1 不接入微信订阅消息推送（用户确认）；报名/支付成功仅通过支付成功页与「我的订单」订单状态告知。订阅消息、优惠券、拼团、分销等营销能力列入后续版本。
- 项目价格以人民币「元」为单位，v1 不涉及多币种。
- 名额以「支付成功并原子扣减的订单数」为准；待支付订单**不**锁定名额，无需超时释放；并发支付中后到者触发原路退款（见 FR-010）。
- 登录态与会话安全遵循微信小程序常规实践（token + 服务端校验）。
